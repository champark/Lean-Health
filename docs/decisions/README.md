# Design Decisions

> Project: Lean Health

이 디렉터리는 **코드가 무엇을 하는지보다 왜 그런 방식으로 만들어졌는지**를 보존하기 위한 설계 결정 기록(ADR, Architecture Decision Record) 공간이다.

README, TODO, 완료 기록만으로는 시간이 지난 뒤 다음을 알기 어렵다.

- 왜 이 구조를 선택했는가
- 어떤 사용자 요구나 버그 때문에 현재 코드가 생겼는가
- 어떤 대안을 검토했고 왜 기각했는가
- 단순해 보이는 다른 구현으로 되돌리면 어떤 문제가 재발하는가
- 성능, 데이터 호환성, UX, 보안 등의 제약이 무엇이었는가

따라서 의미 있는 설계 결정을 동반하는 변경은 이 디렉터리에 기록한다.

## 언제 ADR을 작성하는가

다음 중 하나에 해당하면 새 ADR을 만들거나 기존 ADR을 갱신한다.

- 성능 문제를 피하기 위해 구현 방식이 제한되는 경우
- 데이터 모델, 저장 포맷, 동기화 방식, 캐시, 인덱스가 바뀌는 경우
- 여러 구현 대안 중 하나를 의도적으로 선택하는 경우
- 기존 코드가 복잡해 보이지만 그 복잡성을 유지해야 하는 이유가 있는 경우
- 회귀 버그를 막기 위한 불변조건이나 금지사항이 생기는 경우
- 사용자 요구 때문에 장기적으로 유지해야 할 UX/동작 계약이 생기는 경우
- 이후 개발자가 "왜 이렇게 했지?"라고 다시 판단할 가능성이 높은 경우

오탈자, 문구 변경, 명백한 작은 버그 수정, 포맷팅처럼 설계 판단이 거의 없는 변경까지 ADR을 만들 필요는 없다.

## 파일 규칙

파일명은 다음 형식을 권장한다.

```text
ADR-0001-short-title.md
ADR-0002-short-title.md
ADR-0003-short-title.md
```

번호는 기존 파일의 다음 번호를 사용한다.
이미 기록된 결정이 바뀌면 기존 기록을 몰래 덮어써 과거 맥락을 지우지 말고, 상태와 대체 관계를 명시한다.

## ADR 템플릿

```markdown
# ADR-XXXX: 제목

- 상태: 제안 / 승인 / 대체됨 / 폐기
- 날짜: YYYY-MM-DD
- 관련 작업: TODO, 이슈, 커밋 또는 사용자 요구

## 맥락

어떤 문제와 요구 때문에 이 판단이 필요했는가?

## 결정

무엇을 어떻게 구현하기로 했는가?

## 이유

왜 이 방법을 선택했는가?
성능, UX, 데이터 안전성, 유지보수성 등 실제 이유를 적는다.

## 검토한 대안

### 대안 A
- 장점:
- 단점:
- 채택/기각 이유:

### 대안 B
- 장점:
- 단점:
- 채택/기각 이유:

## 지켜야 할 조건

이 결정을 유지하려면 이후 코드가 무엇을 보존해야 하는가?

## 성능 영향

`docs/PERFORMANCE_REQUIREMENTS.md`에 어떤 영향을 주는가?
측정하지 않았다면 검증되지 않았다고 명시한다.

## 후속 작업

남은 검증, 최적화, 마이그레이션 또는 TODO가 있으면 기록한다.
```

## 변경할 때의 원칙

- 코드를 단순화하기 전에 관련 ADR이 있는지 확인한다.
- 기존 ADR과 충돌하는 변경을 조용히 적용하지 않는다.
- 기존 결정을 폐기해야 한다면 이유를 기록하고 새 결정과 연결한다.
- ADR은 결과를 정당화하기 위한 사후 문서가 아니라 **판단의 맥락을 보존하는 문서**다.
- 성능과 관련된 결정은 반드시 `docs/PERFORMANCE_REQUIREMENTS.md`도 함께 확인한다.
- 성능 요구를 위반할 가능성이 있는 대안은 사용자에게 먼저 알려야 한다.

## 문서 역할 구분

- `README.md`: 프로젝트가 무엇이고 현재 어떻게 동작하는가
- `TODO*.md`: 앞으로 해야 할 일
- 완료 기록: 무엇을 완료했는가
- `docs/decisions/`: 왜 그런 구현과 제약을 선택했는가
- `docs/PERFORMANCE_REQUIREMENTS.md`: 성능상 반드시 지켜야 할 계약
