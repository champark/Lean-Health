# Performance Requirements

> Project: Lean Health (Android health/pedometer app)

이 문서는 이 프로젝트에서 **반드시 보존해야 하는 사용자 체감 성능 계약**을 정의한다.
기능을 더 많이 넣는 것보다 이미 합의된 성능 기준을 깨뜨리지 않는 것을 우선한다.

## 1. 일반 화면 응답성

- 일반적인 페이지·화면·탭·패널 전환은 **사용자 입력 후 1초 이내에 사용 가능한 UI를 표시해야 한다.**
- 전체 데이터 처리가 끝날 때까지 첫 화면 표시를 막아서는 안 된다. 필요한 경우 shell, 부분 목록, 캐시, 점진 로딩을 사용한다.
- 앱이 통제할 수 있는 로컬 계산 때문에 1초를 넘기는 화면 전환은 성능 요구 위반으로 본다.
- 버튼을 눌렀는데 아무 반응 없이 기다리게 만드는 구현을 피한다. 작업이 즉시 끝나지 않으면 진행 상태나 작업 중임을 빠르게 표시한다.

## 2. 긴 작업의 예외와 조건

다음은 작업 자체가 1초를 넘길 수 있다.

- 명시적으로 사용자가 시작한 대량 처리·배치 시뮬레이션
- 파일 복사·이동·가져오기·내보내기
- 동기화, 다운로드, 업로드 등 외부 I/O 또는 네트워크 의존 작업
- 빌드, 테스트, 데이터 마이그레이션처럼 일반 화면 전환이 아닌 개발/관리 작업

그러나 이런 작업도 다음 조건을 지켜야 한다.

- 일반 UI를 이유 없이 장시간 완전히 멈추게 하지 않는다.
- 가능한 경우 작업 진행 상태를 표시한다.
- 긴 작업이 일반 화면 진입의 필수 선행 조건이 되지 않도록 분리한다.
- 외부 서비스 지연을 앱 내부 계산 지연과 혼동해 성능 준수로 주장하지 않는다.

## 3. 데이터 규모에 대한 원칙

- 매 프레임, 매 recomposition, 매 UI 갱신마다 전체 데이터셋을 순회하는 구조를 기본 해법으로 사용하지 않는다.
- 데이터가 늘수록 선형 또는 그 이상으로 커지는 고비용 처리를 사용자 입력의 동기 경로에 넣기 전에 대안을 검토한다.
- 이미 부분 로딩, 캐시, 인덱스, 공간 분할, 증분 갱신 등으로 해결된 병목을 단순화한다는 이유로 되돌리지 않는다.
- 실제 병목을 고치기 위한 최적화는 측정을 우선한다. 측정하지 않았다면 성능이 보장되었다고 표현하지 않는다.

## 4. 성능 회귀 금지

새 기능이나 코드 변경이 이 문서의 요구사항을 위반하거나, **위반할 가능성이 합리적으로 있다고 판단되는 경우 구현자는 이를 조용히 진행해서는 안 된다.**

구현 전에 사용자에게 최소한 다음을 알려야 한다.

1. 영향을 받을 가능성이 있는 성능 요구사항
2. 예상되는 지연·프레임 저하·메모리 증가 등 영향
3. 왜 그 영향이 발생하는지
4. 성능을 유지할 수 있는 대안
5. 기능 범위와 성능 중 어떤 선택이 필요한지

사용자가 기능 추가를 직접 요청했더라도 이 규칙은 그대로 적용한다.

성능 저하가 불가피한 경우에는 **사용자가 그 trade-off를 명시적으로 승인하기 전까지 기존 성능 요구를 조용히 약화하지 않는다.**

## 5. 요구사항 변경 규칙

- 이 문서의 수치나 제한을 코드에 맞추기 위해 사후적으로 낮추지 않는다.
- 요구사항 자체를 변경하려면 그 이유와 영향을 설명하고 사용자의 명시적 결정을 받아야 한다.
- 새 하드웨어나 더 빠른 개발 환경에서만 통과한다는 이유로 회귀를 정상으로 취급하지 않는다.
- 특정 수치를 실제로 검증하지 못했다면 `검증되지 않음`으로 기록한다. 추정치를 검증 결과처럼 쓰지 않는다.

## 6. 검토 체크리스트

성능에 영향을 줄 수 있는 변경 전후에 다음을 확인한다.

- 이 변경이 화면의 첫 usable UI를 늦추는가?
- 기존에 지연/증분 처리하던 작업을 다시 동기 처리로 바꾸는가?
- 데이터 수가 커질 때 비용이 급격히 증가하는가?
- UI thread / main thread / game loop에 새 고비용 작업을 추가하는가?
- 반복 실행되는 경로에 전체 검색·전체 재계산을 추가하는가?
- 측정 없이 "문제없다"고 가정하고 있지는 않은가?

하나라도 위험하다고 판단되면 **구현 전에 사용자에게 성능 위험을 알린다.**
